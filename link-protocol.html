Spaceback Link protocol, version 1

Pairing and session cryptography. Published 27 September 2026. Applies to Spaceback for Mac 2.3 and Spaceback for iPhone and iPad 1.3, and later versions that speak Link protocol major version 1.

Spaceback Link connects Spaceback on an iPhone with Spaceback on a Mac over the local network, so each device can show what the other found. This page publishes the cryptographic parts of that protocol in full: how two devices pair, how they open an encrypted session, and how records are protected.

Every primitive comes from Apple CryptoKit: X25519, Ed25519, P-256 in the Secure Enclave, SHA-256, HMAC-SHA256, HKDF-SHA256 and ChaCha20-Poly1305. The session handshake is exactly Noise_KKpsk2_25519_ChaChaPoly_SHA256 from the Noise Protocol Framework, revision 34. The pairing exchange that establishes the Noise pre-shared key is described in section 2.2.

Section numbers follow Spaceback's internal specification, which this page quotes. Tags such as (A10) or (revision 3.2) mark where a later amendment changed a rule. "iPhone" and "Mac" name the two roles: the iPhone is the initiator (I) and the Mac the responder (R).

Notation

  • H = SHA-256. HKDF(ikm, salt, info, n) = HKDF<SHA256>.deriveKey(inputKeyMaterial:salt:info:outputByteCount:). HMAC(k, m) = HMAC<SHA256>.
  • lp(x) = u32 big-endian length ‖ x. ‖ = plain concatenation. Every variable-length field inside a hashed, MACed or signed message is written with lp; fixed-size fields (keys, digests, integers) are not.
  • wire(Pn) = the exact bytes of frame Pn on the wire, header and body.
  • AEAD nonce, everywhere in this document: 4 zero bytes ‖ u64 little-endian counter, as in Noise §12.3 for ChaChaPoly. One encoding for pairing, handshake and records.

Design decisions

Pairing. X25519 key exchange in which the responder commits first. The 6-digit SAS is derived only from values fixed by the commit/reveal exchange. The Mac shows the SAS, and the user types it on the iPhone, which checks it against its own value. The Mac user then clicks Allow on a sheet that repeats the code. No identity, name or long-term key crosses before the typed code matches. Each device decides grants over its own data.

Sessions. Exactly Noise_KKpsk2_25519_ChaChaPoly_SHA256 (Noise §7.5 KK, §9 psk modifier), built from CryptoKit primitives and checked against published vectors, followed by ChaCha20-Poly1305 records. It is testable without sockets and gives forward secrecy.

2. Pairing

2.1 Identity keys

sign (Curve25519.Signing) is the root identity, and peerID = H(sign.pub)[..16]. agree (Curve25519.KeyAgreement) is the static DH key, certified by sign and proven by the first handshake (§2.2 step 9).

approve (iPhone only) is SecureEnclave.P256.Signing.PrivateKey(accessControl:authenticationContext:).

  • Access control: SecAccessControlCreateWithFlags(nil, kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly, [.privateKeyUsage, .biometryCurrentSet], nil). The CryptoKit default (kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly, no flags) is never used.
  • approveMode is .biometry or .none. There is no passcode mode. With no biometry enrolled, no approve key exists, approveMode = .none, and mac.trash cannot be turned on (§5.1).
  • Biometry change invalidates the key. The iPhone may create a new one only after a fresh .deviceOwnerAuthenticationWithBiometrics evaluation, and sends it with keyUpdate. The Mac then applies the approveKeyPending rule (§2.6). A notification alone is never enough.
  • What approve protects. It stops someone who holds the iPhone but cannot pass its biometry from approving Trash moves through the genuine app. The Mac cannot verify cryptographically that approve.pub lives in a Secure Enclave or is biometry-gated: approveMode is self-reported by a device the user paired. The Mac-side pending rule covers key changes after pairing.
  • Tests: the Simulator uses FakeApprover (SecureEnclave.isAvailable is false there).

2.2 Flow

P0 I→R PairHello   {v, minors, mode: ble|bleReversed|code|digits}                        plaintext ≤4 KiB
       R: v ≠ major, or minors ∩ local minors = ∅ → abort(.versionTooOld), before P1, not counted

P2 I→R PairRevealI {eI.pub, nI, tp = HMAC(token, "SBL1 token" ‖ H(lp(wire P0) ‖ lp(wire P1)) ‖ eI.pub)[..16]}
       R: tp invalid for the current token/code → silent close after 0–300 ms; not counted (§2.3)
P3 R→I PairRevealR {eR.pub, nR}                   I checks c, else abort(.commitMismatch)
       ── the attempt is now CONSUMED on both devices (§2.3) ──
   dh  = X25519(eI, eR)                          any throw → abort(.invalidKey)
   T0  = H(lp(wire P0) ‖ lp(wire P1) ‖ lp(wire P2) ‖ lp(wire P3))
   SAS = UInt64(bigEndian: HKDF(dh, T0, "SpacebackLink v1 SAS", 8)) % 1_000_000         → "482 913"
   kI  = HKDF(dh, T0, "SpacebackLink v1 pairing I->R", 32);  kR = HKDF(dh, T0, "SpacebackLink v1 pairing R->I", 32)
   cI  = HKDF(dh, T0, "SpacebackLink v1 confirm I", 32);     cR = HKDF(dh, T0, "SpacebackLink v1 confirm R", 32)

   Mac shows "Type this code on your iPhone: 482 913". iPhone shows a 6-digit entry field.
   iPhone compares typed code with its SAS in constant time; 3 wrong entries end the attempt.

   PairCodeRejected / PairExtend may precede P4 in either direction (A10, A1); each is a sealed frame
   and each advances that direction's counter.
P4 I→R Seal(kI) PairConfirmI {mac = HMAC(cI, "SBL1 confirm I" ‖ T0), identityI}           sent only after a match
       IdentityI = {sign.pub, agree.pub, approve.pub?, approveMode, cls, name, modelClass, osMajor, appVersion,

   R verifies mac, the identity (PROTOCOL-TV B7: known model, canonical caps, 16-byte installID, known
   cls, sig, pair and window, cls ↔ modelClass, `tv` cap for a TV pair; only a phone may carry an
   approval key), then shows Allow, where its user names the peer (§2.2.1, PROTOCOL-TV B20)
P5 R→I Seal(kR) PairAccept {mac = HMAC(cR, "SBL1 confirm R" ‖ T0 ‖ H(ct4)), identityR, macGrants}
       IdentityR = {sign.pub, agree.pub, cls, name, accountName, modelClass, osMajor, appVersion, caps, installID,
                    sig = Ed25519(signR, "SBL1 identity R" ‖ T0 ‖ signI.pub ‖ agree.pub ‖ u16 macGrants ‖ u8 cls)}

       `name` is sent only by a Mac (its localized host name) and `accountName` only by a Mac; a phone or
       a TV sends "" for both. The receiver sanitises a name and never takes one from a non-Mac.
   I verifies as R did after P4, shows "Linking to <accountName> on <name>" and its own grant screen (§2.2.1)
P6 I→R Seal(kI) PhoneGrants {u16 phoneGrants}                      I's own grants, whatever I's class
   T1 = H(T0 ‖ lp(ct4) ‖ lp(ct5) ‖ lp(ct6))

   R persists PeerRecord + PeerSecrets on a valid S3, then sends record `linkReady`
   I persists on `linkReady`. Both play the linked ceremony.
PairAbort{reason}: plaintext only before P3; after P3 always Seal(kI|kR). A plaintext PairAbort after P3 is ignored.

Sealing (A10, LINK-SPEC §3.1). Seal(k) is ChaChaPoly with the nonce defined in the notation section and the 8-byte frame header as AAD. Two rules that P§2.2 previously left implicit are now fixed:

  • Body shape. Every sealed pairing plaintext is u8 msg ‖ JSON, with msg = 0x01 PairConfirmI (P4), 0x02 PairAccept (P5), 0x03 PhoneGrants (P6), 0x04 PairAbort, 0x05 PairExtend, 0x06 PairCodeRejected. An unknown msg is a sealed-frame failure: the attempt aborts and counts.
  • Counter. Each direction keeps one counter per pairing key, starting at 0 and incremented by 1 for every sealed frame sent in that direction, in send order, whatever its msg. P4 therefore uses counter n, where n is the number of sealed I→R frames sent before it — 0, 1 or 2 rejections, plus any PairExtend.

ct4, ct5 and ct6 are the sealed bodies, including their tags.

PairCodeRejected{attemptsLeft: u8} (A10). The iPhone sends it after a wrong typed code so the Mac can mirror the miss ("That didn't match on your iPhone. 2 tries left."). Without a frame the Mac cannot know, and a Mac that silently keeps showing the same code while the user fails on the phone is the failure mode this closes.

  • Rules. Only the iPhone sends it, only after P3 and before P4, at most 2 per attempt, with attemptsLeft equal to 2 and then 1. The third miss sends a sealed PairAbort{reason: codeMismatch} instead. The Mac aborts — sealed, counted as a failure — on a third PairCodeRejected, on a repeated or wrong attemptsLeft, or on one arriving from the wrong direction. One arriving after a valid P4 is decrypted, to keep the counter aligned, and then ignored. A plaintext 0x01 frame carrying it after P3 is ignored, exactly like a plaintext PairAbort. It does not restart either device's code-entry timer.
  • Not in the transcript. T1 stays H(T0 ‖ lp(ct4) ‖ lp(ct5) ‖ lp(ct6)). The sequence is already authenticated by the counter: a dropped, reordered or injected sealed frame shifts it, so P4 (or the next frame) fails to decrypt and the attempt ends as a consumed failure. The code count is UX information from the device that holds kI, not a security input, so the existing T1 and pairSecret vectors stay valid.

Payload checks.

  • Each side rejects a peer whose sign.pub equals its own.
  • Each side rejects any public key that fails to parse.
  • The Mac rejects approve.pub unless it parses as a P256 x9.63 key, and rejects approveMode == .biometry with no approve.pub (there would be nothing to verify an approval against). Both end the attempt as .invalidKey.
  • A peer's grant report is cut to the half that peer owns: the Mac keeps only phone.* from P6, and the iPhone only mac.* from P5 (§5.1).
  • Pairing payloads are JSON with sorted keys, and u16 grant fields use the fixed bit order of §5.1.

Why nothing after P3 can steer the SAS. The SAS depends only on dh and T0, and both are fixed once P3 is sent:

  • R committed to eR and nR in P1, before seeing eI.
  • I chose eI after P1 and before seeing eR.

A MITM acting as R toward the iPhone must commit before learning eI. Acting as I toward the Mac, it must reveal its key before learning eR. So each leg's SAS is uniform to the attacker until that leg's P3, and nothing sent afterwards (identities, names, grants, randomised Ed25519 signatures) is an input to it. What remains to the attacker is repeated draws, and §2.3 counts each one.

After a match, P4–P6 are authenticated by the AEAD under kI/kR and by the confirm MACs, and T1 binds them into pairSecret. A unit test pins the SAS function's signature to (dh, wire P0…P3).

Why identities come after the code. Before a match, a peer is unauthenticated, so it learns no name, no model, no OS or app version and no long-term public key. The honest iPhone sends IdentityI only after the user has typed the code from the screen they are looking at. The Mac sends IdentityR only after its user clicks Allow.

Timeouts. They are the same values as §3.7:

  • first frame within 3 s of accept;
  • P0–P3 complete within 5 s;
  • code entry 120 s (A1, LINK-SPEC §3.1, raised from 60 s for WCAG 2.2.1);
  • Allow 120 s;
  • iPhone grant screen 120 s;
  • securing 10 s (revision 3.2): from a device's last pairing frame (P6 sent on the iPhone, P6 received on the Mac) until it reports linked. It covers S1–S3, the persist and linkReady. When it runs out, or the connection drops in it, the attempt ends as an interruption (dropped(afterConsume: true), F15), and whatever that device had persisted in the phase is removed again.

Extensions (A1). Code entry and Allow can each be extended once by +120 s, with a new sealed frame PairExtend{phase: codeEntry|allow} (kind 0x04, msg 0x05, allowed once per phase per attempt). Both devices restart that phase's timer on send or on receipt; a second extension for the same phase is refused and the phase times out. Lengthening a timer costs nothing: the MITM bound in §2.3 is counted in consumed attempts, not in wall-clock time.

Extension receipt (revision 3.1). A PairExtend is sent whichever device the user extended on, in every phase it applies to — including the Mac during code entry and the iPhone while it waits for Allow — and every wait that can receive one applies it. If both devices extend the same phase and the two frames cross, the received one is absorbed, because both asked for the same thing; a second local extension of a phase that was already extended still ends the attempt as a timeout.

Leaving mid-ceremony (F21/F22, revision 3.1). Past P3, a device whose app leaves sends a sealed PairAbort{reason} before it closes, in every phase: cancelled when the Mac window closes or the app quits, backgrounded when the iPhone leaves, ambiguous/limitReached when the Mac ends the attempt for those reasons. The other device reports the reason (cancelledOnMac, leftApp, ambiguous, limitReached), never a bare drop, and acts on it at once in every wait — including the Mac's Allow sheet and the iPhone's grant screen, which previously ran out their 120 s. On the grant screen, backgrounded is sent as itself and every other cancel as declinedGrants ("Don't link").

Any abort or timeout wipes the ephemeral keys, dh and every derived key.

Hand-over to the session (revision 3.2, WP2F2). Pairing and the session share one connection, and the iPhone sends S1 straight after P6, so S1 can reach the Mac before the Mac has finished handling P6 — over TCP the two often arrive in one read. The receiving side therefore routes frames by kind until its session takes the connection:

  • While pairing runs, only kinds 0x01 and 0x04 are pairing messages. The first frame of kind 0x02 or 0x03 ends pairing delivery for good: it and every frame after it, of any kind, are kept in arrival order for the session.
  • A session frame that arrives while a device still expects a pairing message (before P6 on the Mac, at any point on the iPhone) is out of order, and the attempt ends as dropped.
  • A pairing frame that arrives after a session frame is the session's to read, and it refuses it.
  • The iPhone is not exposed to the mirror-image race: the Mac sends nothing of the session until it has read S1, and the iPhone switches its reader over before it sends S1. What can cross P6 is a sealed PairAbort from the Mac; during securing the iPhone still opens it and reports its reason.
  • A device that is cancelled during securing (F21/F22) closes the connection without a sealed abort, because the peer is already reading session frames; the peer reports an interruption.

Persist order (revision 3.2). The implementation now follows the flow above literally: the Mac persists the psk and local secrets only after LinkSession.open has verified S3, then sends linkReady; the iPhone persists only after linkReady has arrived. Revision 3.1's code persisted both before S1, so a handshake that failed left secrets behind for a link that never came up. A persist that fails, or a linkReady that cannot be sent, removes what was written (KeyStore.removeAll(for:)).

3. Sessions

3.1 Handshake: Noise_KKpsk2_25519_ChaChaPoly_SHA256

The implementation follows Noise exactly (§5 processing rules, §7.5 KK, §9 psk2) using CryptoKit:

  • DH is Curve25519.KeyAgreement, and any throw aborts with .invalidKey.
  • HASH is SHA256.
  • Noise's HKDF(ck, ikm, n) is computed as HKDF<SHA256>.deriveKey(inputKeyMaterial: ikm, salt: ck, info: [], outputByteCount: 32·n). RFC 5869 with empty info yields the same output1 ‖ output2 ‖ output3 as Noise §4.3. This equivalence is pinned by vectors.
  • CipherState uses ChaChaPoly with the nonce from the notation section.
psk      = epoch secret (pairSecret for epoch 0)
hintKey  = HKDF(psk, "", "SBL1 hint key", 32)
tag8     = HMAC(hintKey, eI.pub)[..8]
prologue = lp("SpacebackLink v1 session") ‖ u8 major ‖ u32 keyEpoch ‖ tag8
           (bulk: lp("SpacebackLink v1 bulk") ‖ u8 major ‖ u32 keyEpoch ‖ tag8 ‖ controlExporter[..16])

KKpsk2:
  -> s                           pre-message: MixHash(agreeI.pub)
  <- s                           pre-message: MixHash(agreeR.pub)
  ...
  -> e, es, ss                   S1 body = tag8 ‖ message1   payload = ClientHello
  <- e, ee, se, psk              S2 body = message2          payload = ServerHello
S3 I→R first transport message: Finished{}
exporter = GetHandshakeHash() after S2 (32 bytes)
Split() → kI2R (I's send), kR2I

The pre-message statics are the agree keys. KK hashes both statics before the first message, and the prologue binds the version, the key epoch and the routing tag. The signing keys and peerIDs enter the pairing transcript (IdentityI/IdentityR signatures, T1 → psk), so the psk binds them too.

In psk handshakes the e token also performs MixKey(e.pub) (Noise §9.2). ServerHello is encrypted with EncryptAndHash, so its AD is the handshake hash, which already covers all of S1 and eR.pub.

Ephemerals. eI and eR are generated inside a single-use HandshakeState for each TCP connection. A second use of the same HandshakeState traps in debug and throws in release, and a test asserts it. R keeps a 10-minute replay cache of eI.pub and rejects repeats.

S1 handling on R.

  • R looks up tag8 among the current and pending epochs of paired peers, and then among tombstones (§2.6).
  • On no match or a failed decryption, it closes silently after a random 0–300 ms.

Authentication. R treats I as authenticated only after decrypting S3. Before S3, the ClientHello payload is exposed to key-compromise impersonation, so R acts only on its version and caps. I treats R as authenticated after S2 decrypts.

Security properties.

  • Forward secrecy: from ee and se.
  • Mutual authentication: from the KK statics plus the psk.
  • Revocation: deleting the psk prevents any new session. Tombstones hold no psk (§2.6).

Hellos. ClientHello{minors, caps} and ServerHello{minor, caps, sessionID} are covered by the handshake hash, which prevents downgrade.

3.2 Records and replay

Records. After Split, each direction is a Noise CipherState with an implicit counter.

  • Records use EncryptWithAd(ad: 8-byte frame header, plaintext). This extends Noise transport, whose AD is empty, and is covered by our own vectors.
  • The counter increments by exactly 1. Over TCP, any replay, gap or reordering fails decryption and closes the connection.

Limits. Rehandshake at 2⁴⁰ records or after 12 h.

Requests. Request IDs are unique per session. Destructive challenges are single-use.

  • Write order (R2, revision 3.1). A record's nonce is its position on the wire, so sealing and sending are one step: each side holds a FIFO gate from before EncryptWithAd until the pipe has taken the frame. Replies, notifications, errors and bye all go through it. Without it, two writers that seal back to back can reach the socket in the opposite order and the receiver closes the connection.
  • Reply slots (R1 of the verification, revision 3.1). A request's reply slot exists before its record is written. A reply, a close, a timeout or a cancellation that arrives while the write is still in progress settles the slot, and the sender reads it when the write returns. A request therefore never waits forever.
  • Request timeout. 40 s (LinkSession.defaultRequestTimeout), the §3.4 liveness bound: a healthy peer is never silent that long, and requests are answered one at a time, so this is also the most a queue of slow handlers may delay one. A timed-out request fails with timedOut and the session stays open. Report it as "Interrupted".
  • Late and unsolicited replies. Only replies carry re. One that matches no waiting request is dropped, never answered — answering it would turn a late reply into an error ping-pong. The exception is an error whose re names one of our notifications: it has no waiter by design and is delivered as an event. An error answering a request this side already gave up on is dropped like any late reply.
  • Back-off. error.retryAfter is in milliseconds. The requester surfaces it with the code (LinkRequestError{code, retryAfter}), clamped to 0…1 h, and waits that long before asking again.
  • Grants checked on receipt. A session checks each message's capability against the grants in force on the link: its own served half plus the peer's half as the peer last reported it (§5.1), each cut to what may cross between the two classes (GrantOwnership.inForce, PROTOCOL-TV B4). The peer's half is what admits the peer's side of a flow that peer serves, such as copy.offer under the iPhone's phone.copy arriving at the Mac. The route check (§4.2, PROTOCOL-TV B3) runs first, so the peer's half never admits a request for our own data.

Truncation. A TCP close without a sealed bye is an interruption. If a request, a page, a Trash commit or a copy was in flight, the UI reports "Interrupted", never completion. A Trash commit's outcome is re-read with trash.result{challengeID} on the next session (§5.2).

4. Framing

4.1 Frame

| kind u8 | major u8 | flags u16 | length u32 BE | body |
kind 0x01 pairing-plain ≤4 KiB (P0–P3, pre-P3 aborts)
     0x04 pairing-sealed ≤16 KiB (P4–P6, sealed aborts, PairExtend (A1), PairCodeRejected (A10));
          plaintext is always `u8 msg ‖ JSON` (A10)
     0x02 handshake ≤4 KiB (S1, S2, Revoked, RevokeNotice)
     0x03 record ≤1 MiB+16

Parsing. LinkFramer uses parseInput and deliverInputNoCopy and hands off to a pure FrameParser. It closes silently on an oversize length, or on a frame kind that is wrong for the current state. Examples: 0x01 after P3; a plaintext PairAbort after P3, which is ignored.

Record plaintext. u32 jsonLen ‖ JSON Envelope ‖ attachment.

  • JSON ≤256 KiB, attachment ≤512 KiB.
  • JSON uses sorted keys; dates are Int64 milliseconds.
